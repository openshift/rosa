# Hyperfleet (Platform API v2) — Architecture & Guidelines

This document describes how the Hyperfleet integration is implemented in the
ROSA CLI, the patterns to follow when adding or extending commands, and the
current gap analysis compared to the HCP (Hosted Control Planes) path.

Last audited: 2026-08-13

---

## Overview

Hyperfleet routes ROSA CLI commands to the **Platform API v2** — a private
REST API exposed through AWS API Gateway — instead of the standard OCM REST
API. The CLI interacts with it through a Kubernetes-style clientset SDK
(generated with `client-go` tooling), but the underlying transport is plain
HTTPS; there is no Kubernetes API server or etcd involved. This provides an
alternative control plane for cluster operations that requires only AWS
credentials, with no Red Hat account or OCM login needed.

Key properties:

- Authentication is AWS SigV4; no OCM token is involved.
- The Platform API is an API Gateway-backed service. Its URL encodes the AWS
  region in the hostname.
- Commands dispatch to the hyperfleet path when `--hyperfleet-url` is set
  (either from the flag or from stored config).
- Hyperfleet and OCM paths coexist in the same binary; the dispatch is a
  runtime check, not a build-time separation.

### SDK design note

The `rosa-hyperfleet-api/clientset` package presents a Kubernetes-style
clientset interface — generated by the same tooling as `client-go` — with
typed resource accessors (`Clusters()`, `NodePools(namespace)`, etc.) and
options structs mirroring `metav1` conventions (`GetOptions`, `ListOptions`,
`CreateOptions`). The underlying transport is plain REST over HTTPS to an AWS
API Gateway endpoint; there is no `kube-apiserver` or `etcd` involved. The
clientset layer is purely a code-generation convenience to keep CLI call sites
idiomatic and testable.

## Runtime Setup — `WithHyperFleet()`

`pkg/rosa/runtime.go`

`WithHyperFleet()` builds the Platform API client and populates the Runtime
without touching OCM. It is the only entry point that commands must call.

### Region resolution (precedence order)

1. `--region` flag / `AWS_REGION` env var (`arguments.GetRegion()`).
2. Extracted from the URL hostname via regex `[a-z]+-(?:[a-z]+-)+\d+`.
3. Error if neither is available.

When both an explicit region and a URL-extractable region are present, they
must agree (`hyperfleet.CheckRegionConflict`). A mismatch is a hard failure
because SigV4 would sign for the wrong endpoint.

> **Note:** `AWS_DEFAULT_REGION` is not read by `arguments.GetRegion()` and
> does not trigger the conflict check. It is picked up only by the ambient
> `aws.GetRegion("")` call used for display (e.g. `rosa whoami`).

### Steps performed

```
ValidateURL(rawURL)
  └─ must be HTTPS

ExtractRegion or GetRegion
  └─ CheckRegionConflict if explicit region provided

awsconfig.LoadDefaultConfig(ctx, WithRegion(region), WithSharedConfigProfile(profile))

sts.GetCallerIdentity → accountID, callerARN

aws.CreatorForCallerIdentity → r.Creator

hyperfleetclientset.NewForConfig(&hfrest.Config{
    Host:      rawURL,
    Region:    region,
    AccountID: accountID,
    CallerARN: callerARN,
    AWSConfig: awsCfg,
}) → r.HyperFleetClient
```

### Testability stubs

All external calls are behind package-level vars so unit tests can replace
them without interface indirection:

```go
var (
    awsLoadConfig  func(ctx, region, profile) (awssdk.Config, error)
    awsGetIdentity func(ctx, awssdk.Config) (*sts.GetCallerIdentityOutput, error)
    hfNewClient    func(*hfrest.Config) (*hyperfleetclientset.Clientset, error)
    hfExplicitURL  func() string
    hfExitFn       func(int)
)
```

## Flag Management — `pkg/hyperfleet/`

### `--hyperfleet-url`

Registered as a persistent hidden flag on the root command in
`cmd/rosa/main.go`. Hidden from help output; intended for internal/preview use.

### Config persistence

The URL is stored in the ROSA config file under `hyperfleet_url` when the user
runs `rosa login --hyperfleet-url <url>`. On subsequent commands, the stored
URL is loaded via:

```go
// cmd/rosa/main.go PersistentPreRun
if !hyperfleet.Enabled() {
    if cfg, err := config.Load(); err == nil && cfg != nil {
        hyperfleet.SetURL(cfg.HyperfleetURL)
    }
}
```

`SetURL` is a no-op when the flag is already set, preserving the
**flag > stored config** precedence.

### Logging out

To clear only the Platform API configuration and fall back to the OCM path on
the next invocation:

```sh
rosa logout --hyperfleet
```

This clears `hyperfleet_url` from the config file while leaving OCM
credentials intact. Without the flag, `rosa logout` removes the entire config
file (existing behavior).

## Command Dispatch Pattern

Every command that has a hyperfleet counterpart uses the same dispatch at the
top of its `run()` function:

```go
func run(cmd *cobra.Command, args []string) {
    if hfEnabled() {
        hfDispatchFn()
        return
    }
    // OCM path ...
}
```

`hfEnabled` and `hfDispatchFn` are package-level vars so they can be replaced
in unit tests. The dispatch closure builds the runtime and calls the execution
function:

```go
hfCreateCluster = func() {
    r := rosa.NewRuntime().WithHyperFleet()
    defer r.Cleanup()
    runHyperfleet(r)
}
```

Keeping the execution function (`runHyperfleet`, `runHyperfleetCreate`, etc.)
separate from the closure is what makes unit testing straightforward — tests
inject a pre-built `*rosa.Runtime` with a mock client.

## Name → UID Resolution

The Platform API identifies resources by UID (server-assigned), not by the
human-readable name the user provides. Resolution helpers in `pkg/hyperfleet/`
list all resources and find the one with the matching name:

```go
// Cluster: name → UID
hyperfleet.ResolveClusterUID(ctx, client, clusterName) (string, error)

// Node pool: name → UID (scoped to cluster namespace)
hyperfleet.ResolveNodePoolUID(ctx, client, clusterUID, nodePoolName) (string, error)
```

Always resolve before any mutation (update, delete) or namespace-scoped list.

## IAM Role Helpers

### Cluster creation

Cluster creation requires the caller to supply `--operator-roles-prefix`. The
seven operator role ARNs are computed deterministically:

```go
hyperfleet.ComputeRolesRef(prefix, accountID, partition)
// → hypershiftv1beta1.AWSRolesRef with ARNs:
//   {prefix}-ingress
//   {prefix}-cloud-controller-manager
//   {prefix}-ebs-csi
//   {prefix}-image-registry
//   {prefix}-network-config
//   {prefix}-control-plane-operator
//   {prefix}-node-pool-management
```

### Node pool creation

The worker instance profile is derived from the cluster's existing roles ref,
so no additional flags are required from the user:

```go
hyperfleet.InstanceProfileFromRolesRef(cluster.Spec.HostedCluster.Platform.AWS.RolesRef)
// Parses NodePoolManagementARN → extracts prefix → returns "{prefix}-ROSA-Worker-Role"
```

## Per-Command Implementation

### Create cluster (`cmd/create/cluster/hyperfleet.go`)

Required flags: `--cluster-name`, `--operator-roles-prefix`, `--subnet-ids`, `--version`.

Flow:
1. Validate required flags.
2. Call EC2 `DescribeSubnets` to derive VPC ID and availability zone from the
   first provided subnet.
3. Compute roles ref via `ComputeRolesRef`.
4. Build HyperShift `HostedCluster` spec and submit via
   `client.HyperfleetV1alpha1().Clusters().Create()`.

### Create node pool (`cmd/create/machinepool/hyperfleet.go`)

Required flags: `--name` (or positional arg), `--cluster`, `--subnet`.

Flow:
1. Resolve cluster name → UID; fetch cluster to extract roles ref.
2. Derive instance profile via `InstanceProfileFromRolesRef`.
3. Build `NodePool` spec with replicas, instance type, instance profile, subnet.
4. Submit via `client.HyperfleetV1alpha1().NodePools(clusterUID).Create()`.

The release image is managed server-side by the Platform API; do not require
or send `--version` for node pool creation.

### Edit cluster (`cmd/edit/cluster/hyperfleet.go`)

Only `--expiration` and `--expiration-time` are supported. All other OCM edit
flags are not applicable to the Platform API spec.

Flow: resolve name → UID → fetch → copy spec → patch expiration → update.

### Edit node pool (`cmd/edit/machinepool/hyperfleet.go`)

Only `--replicas` is supported.

Flow: resolve cluster UID, resolve node pool UID → fetch → update replica count.

### Describe / list

- Describe resolves by name or positional arg; supports `--output` for JSON/YAML.
- List scopes node pools to `--cluster`; outputs tab-separated table.
- Both include a map formatter (JSON/YAML) and a string formatter (human text)
  to match OCM describe/list output style.

### Delete

Both cluster and node pool delete resolve name → UID, confirm via
`confirm.Confirm()`, then call `.Delete()`. Deletion is asynchronous on the
server side.

## Output Conventions

| Mode | How |
|------|-----|
| Text (default) | `hfClusterToString` / `hfNodePoolToString` — label-aligned, matches OCM style |
| JSON / YAML | `hfClusterToMap` / `hfNodePoolToMap` — flat map, nested structs flattened |

Always check `output.HasFlag()` before choosing the formatter.

## Error Handling & Exit Pattern

Hyperfleet command runners do not return errors. On failure:

```go
r.Reporter.Errorf("descriptive message: %v", err)
exitFn(1)
return
```

`exitFn` is a package-level var (`var exitFn = func(code int) { os.Exit(code) }`)
replaced in tests with a panic or no-op so the test can assert failure without
terminating the process.

## Testing

### Unit tests

- Tests live in the same package as the command (`package machinepool`, etc.).
- Inject a `*rosa.Runtime` with `HyperFleetClient` set to a mock.
- Mock chain: `MockInterface → MockV1alpha1PublicInterface → MockClusterInterface / MockNodePoolInterface`.
- Replace `exitFn` with `func(_ int) { panic("exit") }` and assert `Expect(fn).To(Panic())`.

### Generating mocks

```
make generate
```

The `Makefile` runs `mockgen` against the vendored clientset interfaces and
applies a `perl` fixup to rewrite the import path from the vendor-prefixed
form back to the canonical module path.

Do not edit mock files by hand.

### Runtime unit tests

`pkg/rosa/runtime_test.go` tests `WithHyperFleet()` by replacing all
package-level stubs. Each error path has a dedicated `It` block.

## End-to-End Test

**File:** `tests/e2e/hyperfleet_sanity_test.go`
**Label:** `"Hyperfleet sanity"` (Ginkgo focus string used by `make e2e-hyperfleet`)
**Timeout:** 3 hours

### Running the test

```sh
make e2e-hyperfleet HYPERFLEET_URL=https://<id>.execute-api.<region>.amazonaws.com/<stage>
```

Optional environment variables:

| Variable | Default | Description |
|----------|---------|-------------|
| `HYPERFLEET_URL` | — (required) | Platform API v2 base URL |
| `CLUSTER_NAME` | `hf-e2e-<unix timestamp>` | Cluster name (≤ 18 chars — namespace constraint) |
| `OPERATOR_ROLES_PREFIX` | same as `CLUSTER_NAME` | IAM roles prefix |
| `AWS_DEFAULT_REGION` | derived from URL | Fallback region when URL has no region in hostname |
| `HYPERFLEET_VERSION` | empty (server picks default) | OCP version string for cluster creation |
| `HYPERFLEET_INSTANCE_TYPE` | `m5.xlarge` | EC2 instance type for node pools |

> **CLUSTER_NAME ≤ 18 chars:** The Platform API creates a namespace of the
> form `cluster-<36-char-UUID>-<cluster-name>` which must fit within the
> Kubernetes 63-char namespace limit. That leaves exactly 18 characters for
> the cluster name.

### What the test covers

The test is a single `It` block that exercises the full cluster lifecycle end
to end:

1. **Login** — `rosa login --hyperfleet-url` stores the URL in config.
2. **whoami** — verifies `Platform API` and `AWS Default Region` in output.
   `AWS_DEFAULT_REGION` is pinned to the URL-derived region before the
   subprocess runs so that the displayed region is always correct.
3. **VPC setup (direct AWS SDK)** — creates a VPC, private + public subnets,
   Internet Gateway, NAT Gateway, and route tables.
4. **Security group** — creates a worker security group with standard ROSA HCP
   ingress/egress rules.
5. **Private hosted zone** — creates a Route 53 private hosted zone for
   PrivateLink DNS and associates it with the VPC.
6. **Create cluster** — `rosa create cluster --cluster-name --subnet-ids
   --operator-roles-prefix [--version]`. The cluster object is created in the
   Platform API immediately; IAM setup follows.
7. **OIDC provider** — fetches the OIDC issuer URL from `rosa describe cluster`,
   computes the TLS thumbprint, and creates the IAM OpenID Connect provider.
8. **Operator IAM roles** — creates the seven operator roles with OIDC-scoped
   trust policies and attaches AWS managed policies.
9. **Worker IAM role + instance profile** — creates the worker node role and
   instance profile with the deterministic name (`{prefix}-ROSA-Worker-Role`).
10. **Wait for cluster Ready** — polls via SDK `WaitUntil` (interval 30 s,
    timeout 90 min).
11. **List clusters** — `rosa list clusters` and verifies the cluster ID and
    name appear.
12. **Describe cluster** — `rosa describe cluster --output json` and cross-
    checks `id`, `name`, `state`, and `api_url` against a direct SDK `Get`.
13. **Create node pools** — creates two node pools (`np1` with 2 replicas,
    `np2` with 1 replica) via `rosa create machinepool`.
14. **Wait for node pools Ready** — polls each pool (interval 30 s, timeout
    30 min).
15. **List / describe node pools** — `rosa list machinepool` and
    `rosa describe machinepool --output json`, cross-checking IDs.
16. **Delete node pool 2** — `rosa delete machinepool` and waits for deletion.
17. **Initiate node pool 1 deletion** — fires the delete but does not wait;
    PDB on the last pool prevents completion until the cluster itself is
    deleted.
18. **Delete cluster** — `rosa delete cluster` (in `DeferCleanup`).

### Cleanup ordering (LIFO)

`DeferCleanup` blocks registered in order execute in **reverse** order, which
ensures AWS resources are released only after the cluster and its controllers
have stopped creating new resources:

```
cluster deleted + WaitUntil (nil)
  → worker EC2 instances terminated
  → classic ELBs deleted + waited
  → ALBs / NLBs deleted + waited
  → orphaned ENIs released
  → non-default security groups deleted
  → worker instance profile + role deleted
  → operator roles detached + deleted
  → OIDC provider deleted
  → private hosted zone purged + deleted
  → worker security group deleted
  → public route table deleted
  → private route table deleted
  → NAT Gateway deleted + waited
  → EIP released
  → Internet Gateway detached + deleted
  → public subnet deleted
  → private subnet deleted
  → VPC deleted
  → CLI logout
```

This ordering is critical: VPC deletion fails if ENIs, load balancers, or
security groups created by the cluster controllers are still present.

## Checklist for Adding a New Hyperfleet Flag

1. Add the field to the relevant options struct in `pkg/options/`.
2. Register the flag in the command's `AddFlags` function.
3. Update `cmd/rosa/structure_test/command_args/.../command_args.yml`.
4. Implement the flag in the hyperfleet execution function
   (`cmd/{verb}/{resource}/hyperfleet.go`).
5. Map the flag value to the appropriate field in the Platform API spec.
6. Add a unit test in `hyperfleet_run_test.go` (or equivalent) covering the
   new flag on the success path and any new failure paths.
7. Update this document's gap analysis tables.
